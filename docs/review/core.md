## Критично

### К1. Любой посетитель роняет весь сервер (все комнаты) двумя сообщениями
- `server/index.ts:149` — `options` из `create` уходят в комнату без проверки; `src/core/room.ts:665-672` (`host/setup`) проверяет только `typeof`, не значение.
- `src/core/room.ts:718` (`startGame` → `new Authority` → `def.setup`) и `:763` (`restart`) не обёрнуты в try; вызов идёт синхронно из `ws.on('message')` (`server/index.ts:723`). Обработчика `uncaughtException` нет (есть только `unhandledRejection`, `:288`) → процесс Node падает, все партии и комнаты пропадают (systemd перезапустит, но все столы потеряны).
- Сценарий: WS `/ws` → `{t:'create', game:'sea', options:{game:'zzz'}, seats:[{seat:0,kind:'human'},{seat:1,kind:'bot'}]}` → `{t:'hello', clientId:'x', name:'x', ownerKey:<из created>, v:3}` → `{t:'start', fillBots:true}`. `sea/engine.ts:166` `MAPS['zzz']` = undefined → `m.ports` TypeError → сервер упал. Таких игр с «индексом по опции» много; `Number(o.x)` без пределов (например, `akcii` rounds, `danetki` count) дают ещё и зависание/память.
- Как чинить: (1) в `Room` обернуть `new Authority(...)`, `broadcastStep`/`sendStart` (там `def.view`, `def.redact`, `def.result`, `def.toAct`, `def.free`) в try с `roomErrorHook` и закрытием комнаты с ошибкой; (2) общий `cleanOptions(def, raw)` (он уже есть для рекордов в `core/records.ts`) — и в `create`, и в `setup`: только ключи из `def.options`, `select` — только из `choices`, `number` — в `[min,max]`; (3) `process.on('uncaughtException')` с записью в «Ошибки» как последний рубеж.

### К2. Чужое место за столом (и его карты) забирает любой, у кого есть код комнаты
- `src/core/room.ts:341-356` (`pickSeat`), `:314`, `:319`; утечка ключа — `:286` и `:274`.
- Место «узнаётся» только по `clientId`, который клиент присылает сам и который **рассылается всем** в списке голосового чата (`VoiceMember.id`, `voiceList` → `broadcast`, его видят и зрители) и в каждом `rtc.from`.
- Сценарий А (без голоса): идёт сетевая партия на сервере (покер, дурак, мафия — режим «чужие карты не видит никто»). Игрок Б обновил страницу / моргнул интернет. В эти секунды (до 45 с ожидания и дольше) кто угодно с кодом — зритель, или сам соперник А во **второй вкладке** (у вкладки свой `clientId`) — шлёт `hello` → `pickSeat` отдаёт ему «свободное» место Б (`:354`, а ещё раньше — по совпадению имени `:349`), `:319` перезаписывает `clientId` держателя. Он получает `start` с `view` за Б (карты Б) и может ходить за Б. Вернувшийся Б своего места уже не получит (держатель — чужой и онлайн) и станет зрителем.
- Сценарий Б (с голосом): Б в голосовом чате → его `clientId` пришёл всем. Злоумышленник подключается с `hello{clientId: <Б>}` → `:314` выкидывает живое соединение Б, `:348` сажает злоумышленника на место Б. Работает в любой момент, не только при обрыве.
- Усиление во «Вкладышах»: `seatUsers` зафиксированы на старте (`room.ts:727-737`), поэтому захватчик доигрывает за соперника нарочно плохо и выигрывает его настоящие дворовые вкладыши с кона (`server/vkladyshi.ts:340-358`).
- Как чинить: в `welcome` выдавать каждому сидящему секретный `seatKey` (случайный, хранить в sessionStorage рядом с memo), вернуть место посреди партии — только по нему; в голос/`rtc` вместо `clientId` — непрозрачный номер участника в комнате; «любое свободное место» и «по имени» посреди партии на сервере не выдавать (или только с подтверждения хозяина). Второй `hello` на том же соединении запретить.

## Важно

### В1. Рекорды пошаговых игр подделываются: сид и время выбирает клиент
- `src/core/records.ts:210-234` (`verifyReplay`), `server/records.ts:196`.
- Сервер честно переигрывает запись, но `seed` и паузы между ходами (`x[2]`) берёт из присланного. Сценарий: для «Сапёра»/пасьянса/маджонга офлайн перебрать сиды до самой лёгкой раздачи, решить её программой и прислать `log` с паузами по 30 мс (нижний порог — `max(minMs ?? 1000, 30 мс × ходов)`) → первое место в таблице «на время» за всё время. `verified: true` такая строка получает тоже.
- Как чинить: сид раздачи выдаёт сервер (`GET /api/records/seed` → подписанный HMAC `{seed, game, issuedAt}`), рекорд принимается только с этим жетоном и не раньше чем `issuedAt + ms` по часам сервера; жетон одноразовый. Для гостей без сети — таблица «без проверки».

### В2. Оплата «Вкладышей»/покупки засчитывается, а товар может не выдаться никогда
- `server/donate.ts:78-81`: сначала `markDonationPaid` (отдельный запрос), потом `onPaid` (`buy.paid` → `store.grant`, `vk.paid` → `putSaves`).
- Сценарий: база моргнула/таймаут на `grant` или `putSaves` → `result()` бросает, ответ 500 → Robokassa повторяет уведомление → `markDonationPaid` уже `false` → `onPaid` не зовётся. Деньги списаны, монет/«Героев» нет, в логе только «оплачено».
- Как чинить: отметка оплаты и выдача — одной транзакцией, либо отдельный флаг `fulfilled_at`: при повторном уведомлении выдавать, если `paid_at` есть, а `fulfilled_at` нет (выдача идемпотентна: монеты — по номеру заказа в журнале коллекции).

### В3. Повтор уведомления о донате на 299 ₽ дарит месяц «Лавочки+»
- `server/plus.ts:108-115` (`isLinkPayment`), `server/donate.ts:150-153`.
- Если включена подписка по ссылке (`ROBOKASSA_SUBSCRIPTION`), уведомление с суммой 299 ₽ и номером **уже оплаченного** доната считается платежом подписки (`d.paidAt == null` ложно). Сценарий: вошедший игрок с подтверждённой почтой жертвует ровно 299 ₽ (сумма свободная, 10–50 000) → Robokassa присылает уведомление второй раз (не дождалась ответа или дубль) → `linkResult` находит игрока по `EMail` → заказ подписки + месяц прав `video`/`early_access`. Заодно сумма появляется в двух учётах.
- Как чинить: в `isLinkPayment` любой существующий донат с этим номером (оплаченный или нет) — не платёж подписки; лучше отличать платежи подписки по признаку из уведомления (`SubscriptionId`/Shp-параметр), а не по сумме.
- Уверенность средняя: зависит от того, как часто Robokassa шлёт дубли.

### В4. Гонка при входе на сервер: `hello` теряется, стол «висит» без конца
- `server/index.ts:169-171`, `:177-178` и `:723-727`: `created`/`joined` уходит клиенту **до** того, как `attach` дождётся `userOf` + `rights` (2 запроса в базу) и до присвоения `link` в обработчике WS. Пока `link == null` и `pending == false`, все сообщения молча выбрасываются.
- Сценарий: вошедший игрок, сервер в Москве, клиент рядом (RTT 3–10 мс), пул базы занят → `hello` приходит раньше `room.connect` → комната его не видит, но шлёт этому соединению ping, клиент отвечает pong — связь «жива», а `client.waitWelcome()` (`src/core/session.ts:234`, `:262`) ждёт без тайм-аута. Хозяин видит вечную загрузку лобби.
- Как чинить: в обработчике WS складывать сообщения в очередь, пока `handleFirst` не вернул `link`, и проиграть их после; либо слать `created/joined` после `room.connect`. Плюс тайм-аут на `waitWelcome`.
- Уверенность средняя (зависит от задержек базы), но окно гонки настоящее.

### В5. Монеты «Вкладышей» фармятся без дневного предела через сетевые партии
- `server/vkladyshi.ts:360-361`: в `settle` каждому из двух людей — `reward()` за каждую сетевую партию, без `REWARD_GAP`/`REWARD_DAY`, которые есть у партий с ботом (`:199-208`).
- Сценарий: один человек с двумя аккаунтами (два браузера) создаёт серверный стол «Вкладышей», садится за оба места, доигрывает и жмёт «Сыграть ещё» (`restart`) по кругу → +50 дворовых монет за партию без потолка → дворовые жвачки → дворовые вкладыши (их можно ставить на кон и менять).
- Как чинить: тот же счётчик наград (`this.rewards`) и для `settle`; награду за сетевую партию — только разным людям (разные адреса/устройства) и не чаще раза в N минут.

## Мелочь

### М1. Камера без подписки обходится правкой одной строки SDP
- `src/core/room.ts:58-66` (`noVideoSend`) меняет только явные `a=sendrecv`/`a=sendonly` в секции `m=video`. Без атрибута направления секция по умолчанию `sendrecv` (а ещё направление можно задать на уровне сессии). Клиент без права `video` вырезает строку `a=sendrecv` из своего offer — его камеру видят все. В P2P-комнатах проверки нет вовсе (это записано в README). Чинить: в секции `m=video` удалять все `a=send*`/`a=recvonly`/`a=inactive` и дописывать `a=recvonly` (для answer — `a=inactive`), чистить и сессионный уровень.

### М2. Нет пределов частоты на сообщения комнаты и на создание комнат
- `src/core/room.ts:211-227` (`chat`), `:263-276` (`rtc` до 32 КБ), `server/index.ts:141-172`.
- Один клиент шлёт `chat` в цикле → каждое сообщение уходит всем за столом (спам и нагрузка N×M); `rtc` — до 32 КБ за раз без лимита; комнат с одного адреса можно открыть сколько угодно (каждая — свой `setInterval`, у ГОПС ещё и общий таймер 8 мс). Имя в чате может быть «Стол» — подделка системных строк. Чинить: простой ведёрный лимит на соединение (например, 5 чатов/10 с, 50 rtc/с), лимит комнат на адрес, запрет имён «Стол»/«Сервер».

### М3. Сидящий игрок может бесконечно держать паузу
- `src/core/room.ts:232-234`: `hold` по 30 с можно слать снова и снова — боты не ходят (`:938`), игры реального времени стоят (`:797`). Злостный игрок останавливает стол для всех. Чинить: общий бюджет `hold` на соединение (например, 30 с за партию/после каждого `start`).

### М4. Микрофон остаётся включённым, если ушёл со стола во время запроса разрешения
- `src/core/voice.ts:85-109`: `join()` проверяет только `this.joined` после `await getUserMedia`. Если за это время вызвали `destroy()`/`leave()` (ушёл во двор, стол закрылся), `leave()` ничего не сделал (`joined` ещё false), а потом `join` продолжает: берёт микрофон, заводит `AudioContext` и `setInterval` — их уже никто не остановит, индикатор микрофона горит до перезагрузки. Чинить: флаг `destroyed` и проверка его после `await` (остановить дорожки и выйти).

### М5. TURN-логины отдаются кому угодно
- `server/index.ts:565-570`: `/api/ice` без входа и без лимита; отсутствие CORS мешает только чужим страницам в браузере, `curl` получает постоянный `TURN_USERNAME/CREDENTIAL` (или суточный при `TURN_SECRET`). Свой coturn превращается в бесплатный ретранслятор для посторонних (трафик VPS). Чинить: выдавать ICE только соединению комнаты (в `welcome` или по запросу через WS), с коротким сроком и лимитом на адрес.

## В чём уверен не до конца

- **В3** — частота дублей уведомлений Robokassa неизвестна; логика ошибки проверена по коду.
- **В4** — зависит от реальных задержек базы против RTT клиента; окно гонки видно по коду.
- **В5** — скорость фарма зависит от длительности партии «Вкладышей» (сдаться нельзя, но партии короткие).
- Подделка времени нажатия в викторине (`core/clocksync.ts`): клиент, нарочно задерживая `pong`, раздувает `rtt`/`jitter` и тем самым допуск «нажал раньше» (`toRoom` → `clampPress(..., rtt + jitter + 25)`, `rtt` принимается до 10 с). Выигрыш — до сотен мс против честного соседа; в находки не включал, т.к. окно ожидания `pressWin` ограничено 900 мс и реальный выигрыш не проверял.
- Аркадные рекорды (`ARCADE_RECORDS`) принимаются как есть (очки ≤ 1e8) и присланный `label` перезаписывает подпись таблицы (`server/records.ts:179-181`, `:237`) — это записано в README как «проверка правдоподобия», считаю принятым; при желании — не давать клиенту менять подпись существующей таблицы.

## Проверено и выглядит надёжно

- Ход не в свою очередь / за чужое место: `act`/`input` принимаются только для `conn.seats`, очередь проверяет `Authority.act` (`toAct` + `free`); `now`/`win`/`at` в действиях с часами ставит комната.
- Скрытая информация в рассылке: `start`/`step`/`rt` идут только через `def.view(state, conn.seats)` и `def.redact`; журнал (`describe`) строится на клиенте из уже отредактированных событий; снимки (`onSnapshot`) есть только в локальной игре; зрители получают `view(state, [])`. (Утечки — только через захват места, К2.)
- rng: состояние на стороне комнаты, клиенту не уходит, с клиента не управляется (кроме сида рекордов, В1); боты — свой `botRng`.
- Боты: видят только `viewFor([seat])`, ошибки бота пойманы, токен `botToken` гасит устаревшие ходы.
- Robokassa: подпись Result (Пароль #2, `Shp_` по алфавиту), сверка суммы с базой, одноразовость `markDonationPaid`/`payPlusOrder` (транзакция с `for update`), ответ `OK<номер>`.
- Аккаунты: scrypt, хеши сессий и ссылок в базе, одноразовые токены (`useToken` атомарно), лимиты входа/писем, TOTP у Мастера, Мастеру закрыт вход через сервисы.
- OAuth: PKCE S256, state в памяти + httpOnly-cookie `lv_oa` (Path=/api/auth/), `safeBack` не пускает на чужие адреса, обмен кода только на сервере.
- CSRF: POST только JSON + проверка Origin; cookie `SameSite=Lax` (на кросс-сайтовый WebSocket не уходит).
- SQL: все запросы параметризованы; динамические `update ... set` собираются из фиксированных имён столбцов.
- Админка/бэкофис/тексты/подписки/донаты: каждый `admin`-метод проверяет право `master`; Мастера нельзя выдать/забанить из админки.
- XSS: чат, имена мест, `info`, голос, рекорды, ошибки и обращения в админке — через `esc`; имена в `describe` экранирует `table.name()`.
- Статика: `normalize` + `startsWith(DIST)`, загрузки — только `^[0-9a-f]{16}\.(webp|png|jpg|gif)$`.
- `/api/mail/in`: только с 127.0.0.1 без `X-Forwarded-For` + секрет (`timingSafeEqual`), снаружи nginx отдаёт 404.
- Облачные сохранения (`/api/saves`): только игры из `SLUGS` — коллекцию `vk:coll`, журналы `kz:`/`pk:` через них не перезаписать; предел размера и частоты есть.
- «Вкладыши»: купленные монеты (`hcoins`) дают только домашние вкладыши (смешанная оплата — тоже домашние), сдача повторов возвращает домашним — купленные монеты; на кон и в обмен — только дворовые (`checkYard`), отложенные учитываются (`held`), изменения коллекций идут через одну очередь и одну транзакцию.
- Хозяин комнаты: только по `ownerKey` (16 случайных байт на сервере), коды комнат — `randomBytes`.
- Ячейки сохранений (`slots.ts`): подписи экранируются; данные — только свои, в своей вкладке.
